# GGS 服务器架构发展建议

> 配套文档：[服务器架构分析报告.md](服务器架构分析报告.md) · [AGENTS.md](../AGENTS.md) · [README.md](../README.md)
> 用途：作为后续迭代的路线图与实施清单，任务按 `P0-x / P1-x / P2-x` 编号，可逐条推进。

## 0. 现状基线（已核实）

- gactor 已在**框架层**做 panic 隔离：`actorHandleMsg` / `actorLoop` 均 `defer recoverAndLog`（[actor_impl.go](file:///Users/godyy/work/go/godyy/ggs/vendor/github.com/godyy/gactor/actor_impl.go#L285-L300)），并计入 `monitorActorPanic`。
- **业务层无自己的 recover**（`app/` 中无 `recover(`），handler 内 panic 会被吞掉且**不回复**，客户端只能等 RPC 超时。
- 项目代码**无任何指标导出 / 分布式 tracing**，可观测性仅有 `ServiceMonitor` 计数器 + pprof + `/healthz`。
- Actor 迁移能力已具备（三阶段 + 冻结计划 + 租约幂等），但当前 `server : game = 1 : 1`，**未真正启用**。
- `gdconf` 于**启动时**从 MongoDB 加载，暂无运行期热更新。
- 测试较零散（`app/agent/.../router`、`internal/infra/mongobd`、`app/game/.../errs`）。

## 1. 优先级总览

| 优先级 | 方向 | 目标 | 对应任务 |
| --- | --- | --- | --- |
| P0 | 可靠性与可运维性 | 能安稳上生产 | P0-1 ~ P0-5 |
| P1 | 研发工程化 | 改得快、改得稳 | P1-1 ~ P1-4 |

| 横切 | 安全与数据治理 | 贯穿始终 | X-1 ~ X-3 |

**如果只做一件事**：先做 **P0-1（可观测性，尤其邮箱积压指标）**，它也是后续压测、迁移、扩容的前提。

## 2. P0 · 可靠性与可运维性

### P0-1 可观测性从 0 到 1
- **现状**：只有计数器 + pprof + healthz，无指标导出与 tracing。
- **目标**：
  - 暴露 Prometheus 指标：Actor/CActor 数量、**邮箱积压长度**、按 `category × 消息类型` 的 QPS 与处理延迟、RPC 超时率、迁移耗时/失败、`mongobd` 队列深度、Redis/Mongo 连接池。
  - 分布式 tracing：`agent → game → Actor` 全链路，traceID 随协议头 / 登录 token 透传。
  - 日志统一注入 `serverId / playerId / requestId`。
- **落点**：扩展 `ggskit/infra/monitor`；对接 gactor `ServiceMonitor`；在 `app/*/internal/app` 接线。
- **验收**：Prometheus 能抓到关键指标；一次请求可端到端追踪。

### P0-2 慢 Actor / 消息积压治理
- **现状**：无邮箱长度观测，单 Actor 阻塞不可见。
- **目标**：邮箱长度指标 + 阈值告警；单条消息处理耗时埋点，超阈值记慢日志（可定位 DB / 锁 / 计算）。
- **落点**：`internal/infra/actor` 消息处理链 + 监控接线。
- **验收**：压测时可观测到积压与慢消息 Top N。

### P0-3 明确 panic 语义
- **现状**：框架已 recover，但业务 handler panic 被吞且不回复。
- **目标**：业务层统一 `recover → 返回错误响应 + 上报`；对 `monitorActorPanic` 设告警。
- **落点**：`internal/infra/actor/handler` 中间件 / `systems` 统一包装。
- **验收**：注入 panic 的请求能收到错误码而非超时。

### P0-4 优雅停机编排
- **现状**：有 SIGTERM 处理基础（`ggskit/utils/shutdown.go`），但未串起业务时序。
- **目标**：`摘流（注销 registry / agent 停接）→ 迁移或落盘 → 退出`，明确各服务顺序，避免丢脏数据。
- **落点**：各服务 `app/*/internal/app` 启动/停止接线。
- **验收**：滚动重启不丢已改内存数据、不产生「注册仍在但已退出」窗口。

### P0-5 关键路径一致性
- **现状**：脏标记 + 延迟保存有丢失窗口；跨 Actor 无事务。
- **目标**：登录/充值/扣道具等关键操作走「先写后回」强一致 + 幂等键；延迟保存可选加 WAL 或缩短窗口。
- **落点**：`internal/infra/actor/persist`、`internal/infra/mongobd`、各业务 `systems`。
- **验收**：关键操作崩溃后可恢复且不重复扣减。

## 3. P1 · 研发工程化

### P1-1 压测与基准体系
- 用 `app/client` 机器人搭压测框架，建立 **Actor 吞吐 / RPC 延迟 / 迁移 / DB 写入**基准与回归门禁。

### P1-2 集成测试 + CI
- 起 docker（etcd/redis/mongo）跑黄金链路（登录→进游→玩法→落盘）；CI 覆盖构建、`golangci-lint`、单测、`make protos` / `make gen_gdconf` 生成物漂移校验。

### P1-3 配置热更新
- `gdconf` 支持运行期热加载 + 版本回滚 + 变更通知。

### P1-4 协议与错误码治理
- proto 向后兼容规则、协议版本协商、错误码集中登记。

---

## 4. P2 · 业务与规模化

### P2-1 落地 Actor 热迁移
- 结合滚动更新 / 缩容验证热迁移；再推进跨 game 节点迁移（玩家跨服）。

### P2-2 跨服玩法基础设施
- 抽象「逻辑服 ↔ 物理服」映射，作为跨服匹配 / 战 / 聊天的地基（依赖 S2S + 集群路由）。

### P2-3 全局热点服务独立化
- `Server` Actor、排行榜、聊天、活动等拆为独立服务 + Redis 结构 + 分片 / 异步，避免拖累 game 节点。

### P2-4 社交 / 匹配 / 运营系统
- 好友、公会、聊天（补广播、离线消息、跨节点投递）；独立匹配服务 + 队列；邮件 / 公告 / 活动（全局 Actor + 定时 + 后台管理）。

---

## 5. 横切

### X-1 安全
- token 防重放（jti + 过期）、限流 / 防刷、agent 连接限流、协议 fuzz、服务端权威校验防作弊。

### X-2 数据治理
- 玩家数据结构版本化与升级迁移、备份恢复、脏数据修复工具。

### X-3 文档沉淀
- 架构决策（ADR）纳入版本库（当前分析报告在 `.gitignore` 中，仅本地保留）。
